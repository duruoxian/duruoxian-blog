> **最终状态：`reset` 复位链验证（Reset reason 0x54 MPSYSRST）；自定义变量 `mybootnet` / `mybootemmc` 创建并落盘；两条启动路径分别实跑——网络路径（双 TFTP + bootm）与 eMMC 路径（双 ext4load + bootm，全程零 TFTP 字样）都真实点火到预期 panic；`go` 命令认格式。第 4 章《使用 U-Boot》收官。**

## 一、实验目的

1. 掌握 `reset` 复位命令与复位原因寄存器的读法（`Reset reason (0x54): System reset generated by MPU`）；
2. 学会用 `setenv` 创建**自定义复合启动变量**（分号串联多条命令）+ `run` 一键执行，把"网络启动"与"本地 eMMC 启动"做成两条一键路径；
3. 用"拔网线"做对照实验，证明 eMMC 路径完全不依赖网络；
4. 认识 `go` 命令（跳转执行裸机程序）的格式。

## 二、实验环境

| 项目 | 内容 |
|---|---|
| 开发板 | FS-MP1A，trusted 版 U-Boot `g392260b4`，`bootdelay=5` |
| 网络路径依赖 | TFTP 服务器 `192.168.0.100`（实验十三），tftpboot 内有官方 `uImage` + `stm32mp157a-fsmp1a-mipi050.dtb` |
| eMMC 路径依赖 | eMMC GPT 2 号分区 bootfs 内有同名 `uImage` + dtb（实验十五写入/出厂自带） |

## 三、实验原理

U-Boot 的环境变量不只是"参数"，还可以是**命令序列**：值里用分号串联多条命令，`run 变量名` 就按顺序执行——这就是自定义启动脚本。把它和 `bootcmd` 的思想对比：`bootcmd` 是系统自带的默认启动脚本，`mybootnet`/`mybootemmc` 是自己写的双通道启动脚本。配合 `saveenv` 落盘，板子断电后两条路径依然"一键可达"。

## 四、实验步骤（实际执行）

> 全部在 `STM32MP>` 提示符执行。原始日志：`资料/serial_exp17_runvars.log`、`资料/serial_exp17_net.log`、`资料/serial_exp17_emmc.log`。

### 1. 复位命令与复位原因

```bash
reset
```

实测：`resetting ...` 后整条引导链重跑，日志可见 `INFO: Reset reason (0x54): System reset generated by MPU (MPSYSRST)`，5s 倒计时内拦停。

### 2. 扫描分区，确认两条路径的四个文件都在

```bash
ext4ls mmc 1:2
```

实测：清单含 `uImage`（7546640）与 `stm32mp157a-fsmp1a-mipi050.dtb`（71805）。

### 3. 创建两条自定义启动变量并落盘

```bash
setenv mybootnet 'tftp c2000000 uImage;tftp c4000000 stm32mp157a-fsmp1a-mipi050.dtb;bootm c2000000 - c4000000'
setenv mybootemmc 'ext4load mmc 1:2 c2000000 uImage;ext4load mmc 1:2 c4000000 stm32mp157a-fsmp1a-mipi050.dtb;bootm c2000000 - c4000000'
saveenv
printenv mybootnet mybootemmc
```

实测：`saveenv` 回显 `Writing to redundant MMC(0)... OK`；`printenv` 两条变量原样回显，一字不差。

### 4. 跑网络启动路径

```bash
run mybootnet
```

实测关键回显：`TFTP from server 192.168.0.100; our IP address is 192.168.0.8` → `Bytes transferred = 7546640 (732710 hex)` → `Bytes transferred = 71805 (1187d hex)` → `Starting kernel ...` → `Machine model: HQYJ STM32MP157 FSMP1A MIPI Discovery Board` → `[7.07s] Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(0,0)`（预期内）。约 32s 后看门狗复位，倒计时内拦停。

### 5. 拔网线，跑 eMMC 启动路径（对照实验）

拔掉网线后：

```bash
run mybootemmc
```

实测：`7546640 bytes read in 201 ms (35.8 MiB/s)` + `71805 bytes read in 37 ms (1.9 MiB/s)`（两条 ext4load，从 eMMC 本地取文件），随后 `Starting kernel ...`、同一 Machine model、同一预期 panic——**全程日志零 `TFTP` 字样**，证明 eMMC 路径与网络完全无关。看门狗复位后拦停。

### 6. `go` 命令认格式

```bash
? go
```

实测：`go - start application at address 'addr'`——本阶段没有可跳转的裸机程序，只认格式不执行。

## 五、实验结果

| 检查项 | 实测结果 |
|---|---|
| `reset` 复位原因 | `Reset reason (0x54): System reset generated by MPU (MPSYSRST)` |
| 自定义变量落盘 | `printenv` 两条变量原样回显，redundant MMC 写入 OK |
| `run mybootnet` | 双 TFTP 装弹 → 内核点火 → 预期 panic |
| `run mybootemmc`（拔线） | 双 ext4load（35.8 MiB/s）→ 内核点火 → 预期 panic，零 TFTP 字样 |
| `? go` | `go - start application at address 'addr'` |

**结论**：两条一键启动路径真实可用、互为对照；第 4 章《使用 U-Boot》全部实验收官。

## 六、问题与心得

1. **环境变量是 U-Boot 的"脚本引擎"**：`setenv xxx 'cmd1;cmd2;cmd3'` + `run xxx`，把多步操作固化成一条命令——这就是 `bootcmd` 的工作方式，也是产品级 U-Boot 启动方案的原型。
2. **两条路径的差异只在"取文件"**：网络路径靠 TFTP（3 MiB/s 量级、依赖网线与服务器），eMMC 路径靠 ext4load（35.8 MiB/s、无外部依赖）——产品里选后者，开发里选前者，本篇各跑一遍即为对照实验。
3. **整条值必须单引号包住**：值里有分号和空格，丢了引号分号就会把一条变量拆成多条命令执行。
4. **panic 复位后的自动启动**：看门狗复位后倒计时归零会自动跑 `bootcmd`，若 bootcmd 落到出厂 eMMC 系统就会一路启动进 Linux——想回 U-Boot 要么倒计时内拦停，要么 `setenv bootcmd`（赋空）+ `saveenv` 临时关掉。
