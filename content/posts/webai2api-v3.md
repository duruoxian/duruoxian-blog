## 一、网页模型没有 tools 协议，怎么模拟

网页版的输入框里只能发文本。模型不会输出 `tool_calls` 结构，
只会说话。所以整个工具调用是一条「约定 + 解析」的链：

```
注入    把工具清单写进提示词，约定一个输出标记
产出    模型按约定输出标记 + JSON
扣留    流式输出里扣住标记文本，不让它漏进正文
解析    结束后解析成标准 OpenAI tool_calls 下发
回填    客户端执行完，把结果渲染成 <tool_result> 块增量发回
```

标记格式按模型训练时见过的样子选，命中率完全不同：

- 千问用 Hermes 风格 `<tool_call>{json}</tool_call>`——它训练时见过，
  输出最稳；
- Kimi / 智谱用行内标记 `<<<TOOL_CALL>>>{json}`。

这里有一个 v0.1.26 修掉的大坑：**Kimi 网页版的 `systemPrompt` 字段
完全不生效**（CHAT 和 OK_COMPUTER 场景都无视它）。也就是说 v0.1.25
之前，工具协议的注入提示词**从来没有到达过模型**——工具「能用」
纯粹是因为模型偶尔自己悟出了输出格式。修复后协议改为随首条用户
消息投递，命中率才稳定下来。

## 二、抓帧：智谱上游的真相

工具链上线后，GLM 开始出现各种诡异的输出问题：整段重复两遍、
文字交错咬合（「上—你是里的编写你本。后到do早之前楼or」这种
两句话绞在一起的产物）、工具调用的 JSON 碎片漏进正文。

我最初的修复方向全错了——按「上游发的是全量快照」的假设写了
累积器，又按「有重试路径」的假设找重复根因（那个重试路径根本
不存在，重复的真因是我自己流式收尾时把全文重发了一遍）。

最后停掉所有猜测，写脚本直接抓上游的原始 SSE 帧序列，一眼看穿：

```
帧1: parts=[{logic_id: A, think: '用户'}]          ← 2 个字
帧2: parts=[{logic_id: A, think: '要求'}]          ← 2 个字
...
帧30: parts=[{logic_id: A, think: '用户要求...（223字）'}]  ← 全量！
帧31: parts=[{logic_id: B, text: '我是'}]          ← 正文开始
```

**每一帧是增量 delta，只有几个新字；part 结束时才发一帧全量快照
（权威校准）；思考、正文是不同 logic_id 的 part 交错到达。**

而我此前的代码把每帧 delta 当成全量快照做前缀切割——每帧切出来的
是尾巴碎片。丢字、咬字、JSON 漏正文，全部症状一个根因。按真实协议
重写：按 logic_id 累积 delta，finish 帧用全量校准，按首见顺序拼接。

这件事给我的教训刻在这里：**调试第三方流式接口，第一件事是抓原始
帧，不是读代码猜协议。**

## 三、多路候选回答：qwen3.8-max 语无伦次的真相

抓帧还解开了另一个悬案：qwen3.8-max 经常输出语序混乱的内容，
但同款模型在官方网页上一切正常。

在 Qwen2API（GitHub 844 星）的源码里找到了答案——它的
`createUpstreamResponseFilter` 注释精确描述了这个行为：

> 上游偶尔会对同一次请求开启多路候选回答：先连续下发多个
> response.created（chat_id/parent_id 相同，response_index 为
> "0"/"1"，各自 response_id 不同），随后两路增量帧交错到达。
> 解析时不区分 response_id 就会把两路内容拼到一起。

也就是说，千问有时候像赌马一样同时生成两份回答，官方网页只展示
index=0 的那份。我们的中继把两路都收进来按到达序拼——用户看到的
就是两句话 zip 在一起。把这个过滤器移植过来（锁定 index=0，其余
整路丢弃）之后，qwen3.8-max 的语序问题消失。

这也是这个项目第一次**直接移植**别人的实现。之前我对这种「抄」
有点心理障碍，实际上：协议逆向的成果（抓帧确认的行为特征）加上
成熟项目的过滤机制，才是正确组合。

## 四、流式链的三层嵌套错位

修完上游解析，opencode 实测发现 GLM 还是咬字——而且**不带工具
完美，带工具必坏**。差异锁定在流式链路：

```
工具扣留器（回扣15字符防拆包） → 防重复守卫 → 前缀差
```

三层嵌套，每一层都假设输入是「单调递增的全量文本」。但第一层的
回扣机制让输出变短了，第二层的守卫发现「快照被改写」就解除武装
并重置内部状态，第三层的前缀差在错位的状态上继续切——三层各自
都「正确」，组合起来是灾难。

重构后的链路只有一条纪律：**前缀差只对单调全量做，工具标记扣留
改用增量口径（喷新增的字，不喂全文快照）**。防重复守卫整个删掉
——它防的「全文重发」bug 根治之后，它在增量链路里只剩害处。

修完之后用 opencode 实测验收：三个平台的工具任务各写一个文件，
内容逐字正确；GLM 带工具逐字复述《静夜思》三遍，一字不差。

## 五、会话串台：要春望，给静夜思

用户（也就是我自己）在 opencode 里遇到过最诡异的问题：几天前的
会话让 kimi 写过《静夜思》PDF，今天开新会话要《春望》，kimi 却
认认真真生成了一份《静夜思》——它连文件名都叫静夜思.pdf。

这是会话缓存的第二个坑。为了多轮工具链，一段对话要稳定映射到
同一个网页会话，缓存 key 用的是「system 前 200 字 + 开场白前
500 字」。问题在于：**opencode 每个新会话的 system 完全一样**，
只要开场白相近，key 就和几天前的旧会话撞车——新请求被塞进旧
网页会话，模型接着几天前的上下文聊。

修了两层：

1. **首轮强制新建**：请求里还没有 assistant 历史 = 新会话起点，
   绝不查缓存。这一层挡住了大部分场景。
2. **会话指纹锚定首轮回复**：多轮请求的 key 加入「首条 assistant
   的规范化指纹」（工具调用做 JSON 规范化，保证我方发出与客户端
   回传时指纹一致）。模型对相同输入的回复几乎必然不同——两个
   会话哪怕 system 和开场白一字不差，key 也必然不同。

修复的验证方式很直白：写一个「孪生会话」测试——同 system、同
开场白、不同首轮回复，断言 key 必须不同。

## 六、授权卡两次消失事故

客户版面板的授权卡片（输入授权码的唯一入口）消失过两次，两次
根因完全不同：

**第一次（v0.1.26）**：单代码库合并时，把 lite 分支 state 接口里
的一行 `"license": ...` 弄丢了。前端拿不到授权状态，把整张卡当
「未启用」隐藏。这病带了四个版本才被发现——因为界面不报错，
只是东西没了。

**第二次（v0.1.28 装机）**：我装机时把静默参数 `/VERYSILENT`
拼成了 `/VERYSILEST`，Inno Setup 退回交互模式；用户（我自己）
装完点了「立即启动」——安装器是提权进程，拉起的程序继承了
管理员权限，Program Files 目录变可写，程序按「exe 同级优先」
的规则在安装目录**新建了一个空数据库**。用户侧的表现：授权
没了、账号没了。真实数据完好无损地躺在用户目录里，只是没人读它。

这次事故催生了两个永久修复：

- 数据目录逻辑：安装态客户版**永远**用用户本地目录，哪怕 exe
  目录可写；
- 安装器 `[Run]` 段加 `runasoriginaluser`，装完自动启动降回
  普通用户权限。

以及一条用户直接下达的产品需求：**授权卡永不隐藏**。现在前端
无条件渲染这张卡——后端就算报错，也显示成「未激活」+ 输入框，
用户永远有自救入口。配套测试直接在 node 里跑面板的真函数，喂
六种残缺数据断言卡片全部可见。

## 七、opencode 接入的静默丢弃

一键接入功能把配置写进 opencode 的 jsonc。v0.1.27 做 opencode 2.x
适配时迁了 `providers`/`package`/`settings`/`capabilities` 四处，
漏了一个：**variants（推理档位）的格式从对象变成了数组**。

```jsonc
// 旧（对象）—— schema 校验失败
"variants": { "标准": { "reasoningEffort": "low" } }
// 新（数组）
"variants": [ { "id": "标准", "settings": { "reasoningEffort": "low" } } ]
```

结果是一键接入写出的配置 opencode **静默拒绝整个提供商**——不报
错、不写日志，模型列表里就是没有。这个 bug 排查了很久，因为
对照组（另一个 openai-compatible 提供商）恰好没写 variants，
一路把怀疑引向键名、端口、IPv6。

修法本身是一行，但防回归测试写得更有意思：从面板 HTML 里抽出
生成配置的真函数，在 node 里执行，断言输出的 variants 永远是
数组。

## 八、长任务与「轮数耗尽」

有用户反馈长任务跑到一半，模型突然忘光了之前的工作，还自己
总结说「轮数耗尽」。这不是模型的幻觉——是我们自己的防风控
设计：单个网页会话最多 40 轮，超过强制换新会话。新会话里只有
最后一条消息，模型几十轮的工作记录瞬间蒸发。

自用场景下 40 轮太紧。提到 200：长任务能完整跑完，真到 200 轮
的会话本身已经极长，轮换反而健康。

## 九、这一阶段的工作方法

回头看 v0.1.25 → v0.1.32 的十八个提交，真正有效的方法论只有
三条：

**抓数据，不猜协议。** 同一个「输出错乱」症状，我按错误假设修了
三轮都失败；抓一次原始帧，十分钟看到真相。第三方接口的文档
（如果有）永远和实际行为有出入，SSE 尤甚。

**用真实客户端验收。** 单元测试全绿 ≠ 能用。每一轮修复后用
opencode 跑同样的任务（身份问答、写文件、读回验证），很多「测
试通过但实际不可用」的 gap 是这样抓到的。到后来直接用脚本驱动
opencode 跑全模型矩阵，一个模型一个模型过。

**诚实面对「我没测过」。** 有一轮任务失败了，模型如实说「下面
没有任何实测结果，我不编数据」。这句回复让我意识到代理的诚实
是可以依赖的质量信号——人也一样：没跑过的东西就说没跑过，
比编一个漂亮数字有价值得多。

## 十、一点感想

第一篇的结论是「把它当软件做」；第二篇的结论是「细节决定能不能
卖」；这一篇的结论是：**真实使用者的行为，是最高优先级的测试
用例生成器**。

抓帧、复现、二分、验收——这些动作都是被真实使用中的具体症状
逼出来的。如果闭门造车，我到现在还会以为智谱上游发的是快照、
千问的语序问题是模型太差、会话串台是 opencode 的 bug。

另外一个变化是心态上的：早期我倾向「自己发明」，后来发现成熟
开源项目里躺着大量被验证过的机制（Qwen2API 的过滤器、glm2api
的累加器），该移植就移植，代码注释里写清出处。原创性体现在
「把正确的机制放进正确的位置」，不体现在每一行都是自己写的。
